QUESTION 421#center_style_original_202608_0223

認証情報や保存データを盗み出すマルウェアによる被害を予防し、発生時の影響も抑える対策の組合せとして最も適当なものを次から選べ。

  1. 0

    ウイルス対策ソフトだけを導入し、OS更新とアクセス権管理は行わない

  2. 1

    送信元の表示名が知人と同じなら、添付ファイルの種類や文面を確認せず開く

  3. 2

    OS等の更新、最小権限、不審なリンクや添付への注意、切り離したバックアップを組み合わせる

  4. 3

    感染が疑われてもネットワーク通信を続け、調査を避けるためログを削除する

正答と解説を確認

正答2. OS等の更新、最小権限、不審なリンクや添付への注意、切り離したバックアップを組み合わせる

解説

侵入経路を減らす更新と注意、侵害時の権限を絞る最小権限、復旧に使うバックアップを重ねる多層防御が有効と捉えられる。一つの対策では未知の脅威や設定ミスなど全てを防げない。既知の脆弱性を修正する更新や権限管理も必要である。

QUESTION 422#center_style_original_202608_0224

送信元・宛先・ポート番号などに基づく一般的なパケットフィルタリング型ファイアウォールだけでは防ぎにくい脅威を次から選べ。

  1. 0

    規則で拒否対象に指定した外部ポートへ、外部端末が新しい接続を開始する通信

  2. 1

    許可一覧にない送信元アドレスから、内部ネットワークへ到着した受信パケット

  3. 2

    管理者が遮断対象として規則へ登録したプロトコルだけを使う外部との通信

  4. 3

    許可されたHTTPSで偽サイトへ接続し、利用者が本物と思って認証情報を入力する行為

正答と解説を確認

正答3. 許可されたHTTPSで偽サイトへ接続し、利用者が本物と思って認証情報を入力する行為

解説

通信先とのHTTPS接続自体が許可されている場合、暗号化された内容と利用者の判断に起因する認証情報入力は単純なヘッダ規則だけでは判別しにくいといえる。宛先ポートへの新規接続を拒否する規則は、パケットフィルタリング型ファイアウォールが直接実施できる制御である。

QUESTION 423#center_style_original_202608_0225

パスワードに自分の生年月日だけを使うことを避ける主な理由を次から選べ。

  1. 0

    生年月日は公開情報や推測から候補を絞られやすく、試行される可能性が高いから

  2. 1

    数字を一文字でも含むパスワードは、一般的な認証システムでは利用できないから

  3. 2

    生年月日は日付が変わるたびに値も変化するため、同じパスワードとして使えないから

  4. 3

    生年月日を入力すると、長さや保存方式にかかわらず暗号化やハッシュ化が無効になるから

正答と解説を確認

正答0. 生年月日は公開情報や推測から候補を絞られやすく、試行される可能性が高いから

解説

生年月日はプロフィールや会話から知られやすく、取り得る候補も限定されるため、標的型の推測攻撃に弱い。多くの認証システムは数字を含むパスワードを利用できる。問題は数字そのものではなく予測しやすさと捉えられる。

QUESTION 424#center_style_original_202608_0227

指紋認証で本人を誤って拒否する割合を下げるため、照合スコアの受入れしきい値を緩めた。この変更によって一般に起こり得る変化を次から選べ。

  1. 0

    照合基準を緩めると、本人拒否率と他人受入率はともに同じ割合で下がる

  2. 1

    本人拒否率と他人受入率が同時に0になり、精度上の交換関係がなくなる

  3. 2

    しきい値は判定速度だけを変え、本人拒否率と他人受入率には影響しない

  4. 3

    本人を受け入れやすくなる一方、他人を本人として受け入れる割合が上がり得る

正答と解説を確認

正答3. 本人を受け入れやすくなる一方、他人を本人として受け入れる割合が上がり得る

解説

照合条件を緩めることで本人拒否を減らす代わりに、他人受入れが増える可能性がある。受入れ範囲を広げると他人も通りやすくなるため、両方が下がるとは限らないといえる。

QUESTION 425#center_style_original_202608_0232

顔認証のため、顔画像から本人を識別できるように変換した特徴量データを事業者が保有している。このデータの個人情報保護法上の扱いに関する説明として最も適当なものを次から選べ。

  1. 0

    氏名の文字列を含まないため、本人を識別できても個人情報にはならない

  2. 1

    本人を認証できるよう変換した顔の特徴量は個人識別符号に該当し得て、それを含む情報は個人情報となる

  3. 2

    画像そのものではなく数値列へ変換すれば、利用目的にかかわらず匿名加工情報になる

  4. 3

    数字だけで構成されるデータは、法令上の個人識別符号に該当することがない

正答と解説を確認

正答1. 本人を認証できるよう変換した顔の特徴量は個人識別符号に該当し得て、それを含む情報は個人情報となる

解説

本人を認証できる水準で顔の特徴をコンピュータ用に変換した符号は、法令で定める個人識別符号に該当し得るといえる。個人情報かどうかは氏名の有無だけで決まらない。特定個人を識別できる生体特徴の符号を含む情報も対象となり得る。

  1. 0

    ショルダーハッキング

  2. 1

  3. 2

    SQLインジェクション

  4. 3

    IPスプーフィング

QUESTION 427#center_style_original_202608_0235

日本の意匠法で登録による保護の対象となり得るデザインを含むものを次から選べ。

  1. 0

    商品やサービスの出所を識別する文字商標だけ

  2. 1

    自然法則を利用した技術的思想としての発明だけ

  3. 2

    物品の形状等、建築物や内装、一定の要件を満たす画像のデザイン

  4. 3

    思想や感情を創作的に表現した小説の文章だけ

正答と解説を確認

正答2. 物品の形状等、建築物や内装、一定の要件を満たす画像のデザイン

解説

意匠法の対象には物品の形状・模様等に加え、一定の画像、建築物、内装のデザインも含まれ得る。商品・役務の出所を示す名称や標章は主に商標法の保護対象であり、文字商標だけを意匠として挙げるのは不適切である。

QUESTION 428#center_style_original_202608_0246

送信者Xが受信者Yへ文書を送り、第三者に内容を読まれにくくするとともに、Xが署名したことと改ざんの有無をYが確認できるようにしたい。公開鍵暗号とデジタル署名に用いる鍵の組合せとして最も適当なものを次から選べ。

  1. 0

    機密性にはXの公開鍵、署名作成にはYの秘密鍵を用いる

  2. 1

    機密性にはYの秘密鍵をXへ渡し、署名作成にはXの公開鍵を用いる

  3. 2

    機密性にはXの秘密鍵、署名作成にはYの公開鍵を用いる

  4. 3

    機密性にはYの公開鍵、署名作成にはXの秘密鍵を用いる

正答と解説を確認

正答3. 機密性にはYの公開鍵、署名作成にはXの秘密鍵を用いる

解説

Yだけが持つ秘密鍵で復号でき、Xの公開鍵で署名を検証できる正しい組合せである。Xの公開鍵で暗号化するとXが復号する構成になり、Y向け機密性とXの署名作成の両方を満たさない。

QUESTION 429#center_style_original_202608_0247

送信者Xのデジタル署名を受信者が検証する。攻撃者の公開鍵をXのものだと誤認する危険を抑えるための方法として最も適当なものを次から選べ。

  1. 0

    メール本文に添付された公開鍵を、送信経路や指紋を確認せずXの鍵とみなす

  2. 1

    公開鍵の文字列がXの氏名を含んでいれば、証明書の検証を省略する

  3. 2

    署名値が同じ長さであれば、検証に使う公開鍵は誰のものでもよいとする

  4. 3

    認証局の証明書など、信頼できる仕組みでX本人とXの公開鍵の対応を確認してから検証する

正答と解説を確認

正答3. 認証局の証明書など、信頼できる仕組みでX本人とXの公開鍵の対応を確認してから検証する

解説

信頼の連鎖や既知の指紋などにより、検証鍵が本当にXへ属することを確認可能になる。攻撃者が差し替えた鍵を添付可能なので、未確認の経路だけでは本人との対応を保証できない。

QUESTION 430#center_style_original_202608_0248

普段利用しているWebサービスへHTTPSで接続したところ、ブラウザがサーバ証明書について警告を表示した。対応として最も適当なものを次から選べ。

  1. 0

    URL、端末時刻、証明書の対象名・有効期限などを確認し、原因が解決するまで認証情報を入力しない

  2. 1

    URLがhttpsで始まることを正規サイトの証拠とし、証明書警告より優先する

  3. 2

    証明書警告は通信速度だけを示すため、接続相手の確認や暗号化とは無関係だと判断する

  4. 3

    警告の理由を確認せず、ブラウザへ証明書の例外を登録して次回から表示しない

正答と解説を確認

正答0. URL、端末時刻、証明書の対象名・有効期限などを確認し、原因が解決するまで認証情報を入力しない

解説

証明書警告では、URLの入力誤り、証明書の対象名・期限・発行者、端末時刻を切り分ける。警告を非表示にする操作と原因を解決する操作は別である。接続先を検証できない間は、パスワードや個人情報を送らない。
